
АРХИТЕКТУРА PYGRAM
==============================================
Серверless архитектура: Работает в любой локальной сети с SMB-папкой (например, в колледже или офисе).

Сквозное шифрование: AES-256-GCM, RSA-3072. Логины, пароли и сообщения никогда не хранятся в открытом виде.

Группы и личные сообщения: Гибридное шифрование для DM и надежное управление ключами для групп.

Мультиаккаунт: До 3 активных аккаунтов одновременно.

Устойчивость к сетевым сбоям: Специальная логика ретраев для работы с SMB (защита от WinError 5 при блокировке файлов антивирусом).

Богатый UI: Темная тема, кастомизация цветов и шрифтов, реакции на сообщения, отправка файлов и скриншотов (Ctrl+V).

Панель администратора: Гранулярные права (просмотр всех чатов, управление админами), защищенные цифровыми подписями.


Безопасность и компромиссы
=
Проект использует современные криптографические примитивы:

Пароли: Argon2id (time=3, memory=64MB, parallelism=4).

Приватные ключи: Шифруются через Argon2id + AES-GCM (AAD привязка к fingerprint).

Сообщения: AES-256-GCM + RSA-OAEP (гибрид) и подписи RSA-PSS.

Логины: Хранятся в шаре только в виде SHA-256 хеша.

Осознанные компромиссы (by design):
=
Приватный ключ хранится в шаре (зашифрован). Утечка шары позволяет провести офлайн-брутфорс (медленный, но возможный).

Нет Forward Secrecy (компрометация ключа = чтение всей истории).

Администраторы с соответствующими правами могут читать все чаты (модерация).

Использование DPAPI отклонено в пользу мобильности (вход с любого ПК).


## Восстановление супер-администратора (Beta 0.2.6 draft)

- Recovery keypair создаётся отдельно от ключей пользовательской учётной записи.
- Recovery private key хранится в `.admins/superadmin_recovery.json`, зашифрованный Argon2id + AES-256-GCM отдельным паролем восстановления.
- Recovery public key закрепляется в локальном `trusted_root.json` каждого компьютера. Descriptor в общей папке подписывается текущим root; общая папка сама по себе не является источником доверия.
- При восстановлении recovery private key подписывает сертификат перехода, который связывает fingerprint старого root и fingerprint нового root. Это препятствует повторному применению старого сертификата для отката.
- Новый root переподписывает проверенный список администраторов. Все существующие администраторы сохраняют флаги прав; прежняя root-запись становится обычной admin-записью с эквивалентными полномочиями. Новый аккаунт становится единственным супер-администратором и получает все права.
- Recovery-процедура изменяет только `.admins/list.json`, recovery descriptor/certificate и локальный root pin. Она не открывает и не перезаписывает `.meta`, `message`, `files`, `.status`, ключи групп и данные аккаунтов.
- Компьютеры, которые должны автоматически принять будущую смену root, обязаны заранее подключиться к действующему root и закрепить recovery public key. Клиент без такого локального pin не принимает новый root автоматически.

Событийный и синхронизационный контур
====================================

- `EventEngine` — единый диспетчер событий приложения. Файловый транспорт
  публикует `file.created`, `file.modified`, `file.deleted` и `file.moved`.
- `QtSignalBridge` принимает события через `QueuedConnection` и передаёт их
  подписчикам в GUI-потоке. Обработчики интерфейса не выполняются напрямую
  из watchdog-потока.
- `FileTransport` использует один watchdog Observer для нескольких каталогов.
  Открытый чат отслеживает `message/<chat_id>`, `.status` и `.meta`, а не всю
  сетевую папку целиком.
- `ChatViewWidget` обновляет сообщения, удаления, реакции, отметки прочтения,
  присутствие и метаданные группы по файловым событиям. Окно настроек группы
  также обновляет список участников и закрывается при потере доступа.
- `SyncEngine` централизует синхронизацию чатов. Для одного чата не запускаются
  два параллельных прохода; повторные событийные запросы объединяются в один
  дополнительный проход. Синхронизация разных чатов может идти параллельно,
  но число одновременных worker-потоков ограничено тремя.
- `TickEngine` выполняет только резервную сверку: периодическую проверку
  открытого чата, статуса присутствия и списка чатов. Он не заменяет события.

Текущие fallback-интервалы интерфейса: 5 секунд для сверки открытого чата,
2,5 секунды для присутствия и 3 секунды для списка чатов. Одноразовый таймер
сброса статуса набора текста остаётся UI-дебаунсом, а не механизмом синхронизации.
